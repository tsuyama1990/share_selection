# L2 詳細設計：C9 追い風の検知（Tailwind Watch）

作成：2026-10-18 ／ 状態：**設計（受け入れ待ち）**　親：`L1_architecture.md` C9（R8〜R13、N7）　方針と根拠：`docs/tailwind_watch_design.md`（ユーザー承認）　対応テスト：結合テスト（9 章）、E2E は L1 の E9〜E12

凡例：✅ 実装済み ／ 🆕 未実装

**実装の前提**：方針の文書 8 章の段階 0（過去の制度の追い風で、段階ごとの日付と株価の動き始めを並べる）を通ること。段階 0 で「案」より前に株価が動き切っている出来事が大半なら、本書の 4〜6 章を見直す。

## 1. 責務

官公庁の一次情報から、需要を変える制度の出来事を週 1 回拾い（R8・R9）、出来事ごとに段階と期限を台帳に記録し（R10）、全上場企業から需要に売っている会社を引用つきで特定し（R11）、Value Turn の足切りと二次調査の結果を添えて通知する（R12）。通知しなかったものも含めて記録し、後の採点に使う（R13）。最終判断は人。

## 2. モジュール

| モジュール | 責務 | 状態 |
|---|---|---|
| `govfeed.py` | 情報源ごとの取り込み：RSS・一覧のページの解析、案件のページの項目（案件番号・日付）、添付の PDF の本文（`webfetch.py` の PDF の文字化を使う）。許可リストの外へは取りに行かない | 🆕 |
| `triage.py` | 選別と項目の抜き出し（LLM、`verify.py` の引用の照合）、確度と期間の規則（4 章） | 🆕 |
| `ledger.py` | 台帳（`tailwind.db_file`、git 対象外）：案件、出来事、段階の日付、（出来事, 会社）の組、通知、評価の記録 | 🆕 |
| `company_map.py` | 会社の地図：需要から検索語を作り（LLM）、文書ストアの「事業の内容」を検索し、上位の会社を LLM で確かめる（引用つき） | 🆕 |
| `tailwind.py` | `watch` の流れ（取り込み → 選別 → 台帳 → 地図 → 足切りの結果の参照 → 二次 → 通知）、`tailwind-eval` の流れ、通知の Markdown | 🆕 |
| `collect.py`（C2） | `profiles` の流れ：全銘柄に既存の `fetch_annual_report` を回す（`docs` と同じ節を入れるので、後の `docs` は取得済みとして飛ばす）。`docs` に銘柄の指定を足す | ✅ |
| `review.py`（C4） | 二次調査（既存）。`watch` が足切りを通った地図の会社を渡す | ✅ |
| `records.py`（C5） | 最新の実行の全銘柄の判定（通過・落ちた条件）を読む（既存の `screen_results`） | ✅ |
| `review_store.py`（C5） | 地図の会社の最新の T1 の需要の波を読む（追跡、方針の文書 6.6） | ✅ |

## 3. 処理の流れ

### 3.1 `watch`（週 1 回）

```
前提：tailwind-eval の合格の記録（プロンプトの版と最初のモデル）。無ければ拒否（終了コード 1）
 1. 取り込み（govfeed.py）：情報源ごとに新しい案件（台帳に無い (source, item_id)）を取り、案件のページと添付の PDF の本文を得る。失敗は案件ごとに記録して続ける
 2. 選別（triage.py）：案件ごとに LLM が「需要を変える制度の出来事か」と項目（5 章）を引用つきで返す。照合できない項目は空
 3. 台帳（ledger.py）：案件番号で既存の出来事に結び、段階と日付を足す。新しい出来事なら作る。機械で結べないものは、似た出来事の候補として通知に示す（6.2）
 4. 確度・期間（triage.py の規則、4 章）：出来事ごとに計算し直す
 5. 地図（company_map.py）：地図が無いか、需要の項目が変わった出来事について会社を特定し、組を台帳に記録する
 6. 足切りの結果（records.py）：地図の会社ごとに、最新の実行の通過・落ちた条件を組に写す（足切りはやり直さない）
 7. 二次（review.py）：通知の対象（7 章）の出来事で足切りを通った会社のうち、まだ調べていない会社を既存の docs → review の流れに渡す（上限 `tailwind.max_review_tickers`）
 8. 通知（tailwind.py）：7 章の形の Markdown を `tailwind.alert_dir` に書き、通知した組を台帳に記録する
```

同じ週にもう一度実行しても、1・5・7 は取得済み・地図済み・調査済みを飛ばし、8 は同じ内容を上書きする（行は増えない）。

### 3.2 `profiles`（年 1 回＋月 1 回の差分）

```
 1. EDINET の索引を更新（既存の update_index）
 2. 銘柄一覧の全銘柄について、最新の有価証券報告書が文書ストアに無ければ fetch_annual_report（既存。edinet.sections の節）
 3. 失敗は銘柄ごとに記録して続ける。取得済みは飛ばす
```

### 3.3 `tailwind-eval`

正解のある案件（`eval/tailwind_cases.yaml`）で選別と項目の抜き出しを採点し、合否を台帳に記録する。不合格は終了コード 1（8 章）。

## 4. 段階・確度・期間の規則（方針の文書 D2）

### 4.1 情報源と段階

| 情報源 | 取り込む単位 | 段階 | 日付 |
|---|---|---|---|
| e-Gov 募集（`pcm_list.xml`、案件のページ `PCMMSTDETAIL`） | 案件（案件番号） | 案 | 案の公示日 |
| e-Gov 結果（`pcm_result.xml`、案件のページ `PCM1040`） | 案件（案件番号） | 確定（＋ページに公布日があれば公布） | 結果の公示日、命令等の公布日 |
| 首相官邸の閣議案件（日付ごとの一覧） | 案件（閣議の日付と案件名） | 法律案・予算案は案、政令・閣議決定（基本方針・計画）は確定 | 閣議の日付 |

段階の順：案 → 確定 → 公布。施行と期限は日付の項目（5 章）として持つ。e-Gov の募集と結果は、両方のページに載る案件番号で結ぶ [データ：2026-10-18、案件番号 595320006・620340009 のページで確認]。

### 4.2 確度（規則。値は `config.yaml`）

| 強制の種類 | 段階：案 | 段階：確定以上 |
|---|---|---|
| 義務（法令・告示・基準で対象に求める） | 中 | **高** |
| 予算・補助（金額や事業が書かれている） | 中 | **高** |
| 推奨（指針・ガイドラインで促す） | 低 | 中 |
| 該当なし（需要を変えない） | — | — |

### 4.3 期間

期間 ＝ 期限 − 確定の日。期限は、5 章の「施行日」と「経過措置の終わり」のうち遅いほう。予算は年度の終わり。どれも引用で支えられなければ期間は「不明」で、通知の対象にしない（記録は残す）。半年の基準（`tailwind.min_duration_days`、182 日）は方針の文書 3 章のユーザー決定。

## 5. 選別のインタフェース（`triage.py`）

入力：案件の題名、案件のページの本文、添付の PDF の本文（1 件の文字数の上限 `tailwind.max_doc_chars`）。出力（JSON、`research.py` と同じ claims の形）：

```json
{"answer": {"relevant": true, "event": "...", "demand": "誰に何の支出が増えるか", "enforcement": "義務|予算|推奨|該当なし",
            "target": "...", "effective_date": "YYYY-MM-DD|unknown", "transition_end": "YYYY-MM-DD|unknown",
            "budget_amount": "文書の表記のまま|unknown"},
 "claims": [{"field": "...", "claim": "...", "quote": "逐語引用", "doc_id": "..."}],
 "unknown": [...]}
```

- `relevant` が false の案件は、理由の 1 文とともに案件として記録するだけ（出来事は作らない）
- 引用の照合は `verify.py` をそのまま使う。照合できない項目は unknown に置き換える（N3）
- LLM は確度と期間を判断しない（4 章の規則で機械的に決める）
- プロンプトは `prompts/tailwind/` に置き、版は内容のハッシュ。版が変われば `tailwind-eval` をやり直す（`review` と同じ仕組み）

## 6. 台帳（`ledger.py`、`tailwind.db_file`）

### 6.1 表

| 表 | 主キー | 列 |
|---|---|---|
| `feed_items` | (source, item_id) | url、title、published、fetched_at、status（取得済み／取得失敗）、error、relevant、reason、event_id |
| `events` | event_id | title、demand、enforcement、target、effective_date、transition_end、budget_amount、confidence、duration_days、evidence（照合できた主張の JSON）、prompt_version、llm_provider、updated_at |
| `event_stages` | (event_id, stage) | date、source、item_id |
| `event_links` | (event_id, candidate_event_id) | reason、resolved（人が結んだか） |
| `event_companies` | (event_id, ticker) | tier、exposure、evidence、verified_ratio、run_id（足切りを参照した実行）、gate_passed、fail_rule、reviewed_run_id、mapped_at |
| `alerts` | (week, event_id, ticker, kind) | kind は 新規／段階が上がった／期限まで半年／数字に出始めた候補 |
| `tailwind_evals` | (prompt_version, model, evaluated_at) | 正答率などの指標、passed |

Parquet の書き出しは `tailwind.export_dir`（git 対象外。公開リポジトリに会社ごとの判断を載せない。`review` と同じ扱い）。`backup` の対象に `tailwind.db_file` を足す。

### 6.2 出来事のまとめ方

- 機械で結ぶ：e-Gov の案件番号が同じ案件は同じ出来事
- 候補として示す：首相官邸の案件と e-Gov の案件、別の案件番号どうしで、需要と根拠の法令が近いもの（LLM の判定、引用つき）。`event_links` に入れ、通知に「同じ出来事の可能性」として載せる。人が結んだら resolved。自動では結ばない（方針の文書 6.3 の未確認点）

## 7. 会社の地図（`company_map.py`）

1. 検索語：出来事の需要から、製品・サービス・業界の言葉を LLM に挙げさせる（`tailwind.map.max_terms` 語まで）
2. 検索：文書ストアの全銘柄の「事業の内容」とセグメント情報の節を正規化（NFKC）し、検索語の部分一致の数で順位を付ける。上位 `tailwind.map.top_k` 社を次へ。新しい依存（埋め込みのモデルなど）は入れない。取りこぼしが多ければ（段階 2 の関門）検索の方法を見直す
3. 確かめ：会社ごとに LLM が「その需要に売っているか」「何次の供給元か」「売上に占める割合」を引用つきで返す（`research.py` の T1 と同じ項目）。`verify.py` で照合し、売っていることが照合できた会社だけを組にする。`Company.mentioned_in` で別の会社の文書を防ぐ
4. 何次の供給元かは記録するが、通知の条件には使わない（方針の文書 D4）

## 8. 品質の関門（`tailwind-eval`）

| 項目 | 内容 |
|---|---|
| 正解のファイル | `eval/tailwind_cases.yaml`：案件の本文（取得済みの写し）と正解（relevant、enforcement、effective_date、transition_end）。需要を変える案件と変えない案件を両方含める。例：省エネ法のサッシの性能の基準の改正（案件番号 620340009、需要を変える）、ワシントン条約の輸入手続の改正（595320006、変えない） |
| 指標 | relevant の適合率と再現率、enforcement の一致率、日付の一致率、照合率 |
| 合格基準 | L3 で正解の件数と合わせて決める。`review-eval` と同じく、記録が合格でない版・モデルでは `watch` を拒む |
| 正解の確かめ | 正解はユーザーが確かめてから使う（`review-eval` の正解と同じ扱い） |

## 9. 通知（`tailwind.py`、Markdown）

週ごとに 1 ファイル（`tailwind.alert_dir/<週>.md`）。

1. 通知の対象の出来事（確度が高く、期間が 182 日以上）：出来事・需要・段階と日付・期限・引用・出典の URL。会社ごとに、何次か、足切りの結果（通過／落ちた条件）、二次の提案（採用・落選・監視）
2. 段階が上がった出来事、確度か期間が足りない出来事の一覧（短く）
3. 期限まで半年を切った出来事と、その地図の会社（追い風の終わり。方針の文書 D5）
4. 地図の会社のうち、最新の Value Turn の T1 が同じ需要の波を挙げた会社（「数字に出始めた」候補。人が判断する）
5. 同じ出来事の可能性（6.2）
6. 取り込み・選別・地図の失敗の数

メールなどへの送り方は方針の文書 11 章の未決事項（先送り：ユーザーが決める。ファイルの出力で使い始められる）。

`tailwind:`（`db_file`、`export_dir`、`alert_dir`、`sources`（情報源ごとの URL と段階の対応）、`allowed_hosts`（N7 の許可リスト）、`max_items_per_run`、`max_doc_chars`、`min_duration_days`、`confidence`（4.2 の表）、`map.max_terms`、`map.top_k`、`max_review_tickers`、`prompts_dir`、`eval_cases`）。呼び出しの間隔は既存の `throttle.py` と各情報源の `request_interval_s`。

## 11. 結合テスト計画

情報源・EDINET・LLM はモック、DB は一時ファイル。フィクスチャの案件のページは 2026-10-18 に取った実物の形（案件番号 595320006 の結果、620340009 の募集）にそろえる。

| ID | 対象 | 確かめること | 状態 |
|---|---|---|---|
| I-C9-1 | `govfeed.py` とモックの HTTP | 募集と結果の RSS・案件のページから案件番号・段階・日付を取る。閣議案件の一覧から日付と案件名を取る。添付の PDF の本文。許可リストの外の URL は取りに行かず失敗として記録。1 件の失敗で他の案件が止まらない | 🆕 |
| I-C9-2 | `triage.py`＋`verify.py`＋偽の LLM | JSON の検証と 1 回の再依頼、照合できない項目は unknown、relevant が false なら出来事を作らない、確度と期間の規則（4.2・4.3 の表の全マス、期限が不明なら期間も不明） | 🆕 |
| I-C9-3 | `ledger.py`（一時 DB） | 同じ案件番号の募集と結果が 1 件の出来事になり段階と日付が足される。もう一度入れても行が増えない。6.2 の候補は自動で結ばれない。Parquet の書き出し | 🆕 |
| I-C9-4 | `company_map.py`＋文書ストア＋偽の LLM | 検索で正解の会社が上位 `top_k` に入る（フィクスチャの「事業の内容」）。照合できない「売っている」の主張の会社は組にならない。別の会社の文書は使わない | 🆕 |
| I-C9-5 | `profiles` の流れ（`collect.py`）とモックの EDINET | 全銘柄の最新の報告書の節が入る。失敗は記録して続ける。2 回目は取得済みを飛ばす。後の `docs` がその銘柄の EDINET の取得を飛ばす | 🆕 |
| I-C9-6 | 通知（`tailwind.py`）＋台帳＋記録 | 通知の対象の条件（確度・期間）、足切りの結果と落ちた条件の写し、期限まで半年の節、T1 の需要の波の節、同じ出来事の可能性の節。キーが出力に出ない | 🆕 |
| I-C9-7 | `tailwind-eval`（偽の LLM・一時 DB） | 正解との一致で合否、記録、合格の記録が無い版では `watch` が拒む（拒否は E2E の E12） | 🆕 |

E2E（L1 E9〜E12）は、複数週・複数案件で `watch` を通しで実行し、通知のファイルまで出ることを確かめる。

### 11.1 ライブ確認の予定（実装の後に L1 7.1 へ移す）

| シナリオ | 確かめること |
|---|---|
| e-Gov の 2 つの RSS と案件のページ | 案件番号・日付が取れる。PDF の本文が取れる |
| 首相官邸の閣議案件 | 直近の閣議の案件名と日付が取れる。案件の本文の取り方（PDF）を確かめる |
| `profiles`（3 銘柄） | 「事業の内容」が入る |
| `tailwind-eval` | 合否と記録が一致 |
| `watch`（一時ディレクトリ） | 通知のファイルが出る。キーがどこにも出ない |
