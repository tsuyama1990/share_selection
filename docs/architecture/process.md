# 開発プロセス：関門付きの修正ウォーターフォール

作成：2026-10-14 ／ 状態：**適用中**

AI はコードを速く大量に作るため、作ったものを追いきれなくなる。そこで、設計を上から順に固め、各工程の出口に**機械的に止める関門（ゲート）**を置く。純粋なウォーターフォールではなく、関門で失敗したらその工程に戻り、小さな単位で何度も回す。

## 1. 工程と関門

```
L1 全体設計 ─▶ L2 詳細設計 ─▶ L3 クラス設計 ─▶ 実装
   │ E2E           │ 結合テスト      │ 単体テスト
   ▼               ▼                ▼
 各工程：設計 ─[設計の関門]─▶ テスト ─[テストの関門]─▶ 実装 ─[実装の関門]─▶ bonsai ─[保守性の関門]─▶ マージ
```

| 関門 | 止める条件（すべて機械で判定） | 仕組み |
|---|---|---|
| **設計の関門** | 追跡表に抜けがある（要件にコンポーネントや E2E がない）／設計書のモジュール一覧と `src/` が一対一でない／未決事項が「決定」か「先送り（理由付き）」になっていない | `tests/unit/test_design_docs.py`（L1 から導入） |
| **テストの関門** | 計画したテストが無い／階層の印（`e2e`・`integration`・`unit`）が無い／先にテストを書いた工程で、実装前にテストが失敗していない | pytest のマーカー（`--strict-markers`）、ディレクトリと印の一致チェック |
| **実装の関門** | `scripts/gate.sh` のどれかが失敗（ruff、format、mypy、vulture、deptry、pytest、カバレッジ 85%、コード予算） | フック（Stop）、pre-commit、CI、`merge-to-main.sh` |
| **保守性の関門** | bonsai をしていない／純増行数の理由がない／設計書・README が実装と食い違う | ブランチごとに bonsai を実施し、マージメッセージに純増減と削除内容を書く |

関門で失敗したら、その工程に戻る。先の工程に進んで後から直すことはしない。同じ関門で 3 回失敗したら止めて、何が通らないかを報告する。

## 2. テストの階層

| 階層 | 置き場所 | 対象 | 外部システム |
|---|---|---|---|
| E2E（`e2e`） | `tests/e2e/` | L1 の E2E 計画（E1〜E6）のシナリオ。コマンドを通しで実行し、5 章のデータ形式を確かめる | すべてモック・フィクスチャ |
| 結合（`integration`） | `tests/integration/` | L2 の各コンポーネントと、つながる相手（一時 DB、モックの HTTP など） | モック |
| 単体（`unit`） | `tests/unit/` | L3 のクラス・関数 | なし |
| ライブ確認 | CI に入れない | 本物の API の疎通（`llm-check`、`calendar`） | 本物 |

## 3. 進め方の単位

- 1 つのブランチは、1 つの工程の 1 つのまとまり（例：「L1 の E2E テストを揃える」「C4 の L2 設計」）。大きくしない。
- ブランチごとに bonsai を行う（保守性の関門）。コードを足したら、同じブランチで要らなくなったものを消す。
- 変更は上から下へ：設計書 → テスト → コード。設計にないモジュールは関門で落ちる。
