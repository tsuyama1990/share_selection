# 二次スクリーニング自動化 設計書

作成：2026-10-14 ／ 状態：**設計レビュー待ち**（実装前）

根拠の表記は `docs/hypothesis_map.md` と同じ（[原著] [一次] [報道] [データ] [推論]）。段階は `docs/selection_flow.md`、記録は `docs/record_design.md`。

## 0. 目的と範囲

一次スクリーニングの二次候補（`Stage2_Candidate`、現在 50 銘柄/回）について、選定フロー段階 3・5 の調査を LLM と一次情報で自動化し、**銘柄ごとの調査メモと採否の提案**を作る。

- 自動化する：改善の源泉の特定（段階 3）、改善の質と資本の使い方の確認（段階 5）、「忘れられている理由」の分類
- 自動化しない：最終の採否と売買（段階 6）。人が調査メモを読んで決める
- 前提 [原著・手法書]：LLM はもっともらしい取引関係を捏造することがある（レイヤーマスター手法書 Step 3-4）。**一次情報の裏付けがない主張は使わない**ことを、仕組みで保証する（3 章）

## 1. 入力（銘柄ごと）

| 入力 | 内容 | 取得 | 制約 |
|---|---|---|---|
| 一次スクリーニングの記録 | 指標、改善区分、`Quality_Flags`、次回決算日 | `screen_results`（実装済み） | なし |
| 有価証券報告書（最新） | 事業の内容、セグメント情報、主要な販売先、経営方針・中期経営計画、株主の状況 | EDINET API v2：日付ごとの書類一覧 → 書類 ID で取得（XBRL・PDF・CSV）。有価証券報告書は書類種別 120 [報道] | **API キーが必要**（メール登録で無料発行 [報道]）。ユーザーの登録が必要 |
| 決算短信（直近） | 特別利益・特別損失、業績予想とその修正、セグメント別の説明 | TDnet（適時開示情報閲覧サービス） | 公開は直近 31 日分のみ [報道]。決算期ごとに収集し保存する必要がある |
| 会社の IR ページ | 決算説明資料、中計 | 後回し（フェーズ 2） | サイトごとに形式が違う |

注：有価証券報告書は全文が長い。必要な節（事業の内容、セグメント、主要な販売先、経営方針）だけを抜き出して LLM に渡す [推論：Groq・Cerebras などは文脈長が短いモデルがある。要確認]。

## 2. 調査タスク（LLM）

各タスクは「渡した文書だけを根拠に答え、分からなければ unknown」と指示し、JSON で返させる。

| タスク | 段階 | 問い | 出力の主な項目 |
|---|---|---|---|
| T1 改善の源泉 | 3 | 改善はどこから来たか。需要の波（AI・防衛など）、値上げ、コスト、資本政策のどれか。何次の供給元で、何を押さえているか | `source_type`（P1〜P4）、`demand_wave`、`tier`、`chokepoint`、`exposure_pct`、根拠 |
| T2 一時的な損益 | 5 | 直近の利益に、特別損益・資産売却などの一時的な要因がどれだけ含まれるか | `one_off_items`（項目と金額）、`recurring_view`（持続／一時的／不明）、根拠 |
| T3 資本の使い方 | 5 | 現金の使い道、自社株買い・配当方針、大型投資・買収の予定 | `capital_actions`、`n2_risk`（前提崩壊の兆し）、根拠 |
| T4 忘れられている理由 | 3 | 期待が低い理由は、事業の弱さ／見えにくさ／期待先行／一時的な悲観のどれか（`docs/hypothesis_map.md` H2・H4） | `reason_forgotten`、根拠 |
| T5 総合 | 6 の材料 | T1〜T4 を踏まえた採否の提案と、確認すべき点 | `suggestion`（採用／落選／監視）、`open_questions` |

各主張の根拠は `{"claim": ..., "quote": 文書からの引用, "doc_id": ...}` の形で返させる。

## 3. 捏造を防ぐ仕組み（引用の機械照合）

1. LLM の回答に含まれる各 `quote` が、渡した文書の本文に**実際に含まれるか**を機械的に確かめる（空白・全角半角を正規化した部分一致）。
2. 照合できなかった主張は捨てる。各銘柄の「照合できた割合」を記録する。
3. 照合できた主張だけで、タスクの結論が支えられるかを確かめる。支えられなければ、その項目は unknown にする。
4. モデル名・プロンプトの版・温度（0）を記録し、後から同じ条件で比べられるようにする。

[推論] これで「存在しない取引関係」や「文書にない数字」の大半は機械的に取り除ける。文書の読み違い（引用は正しいが解釈が誤り）は残るので、最終判断は人が行う。

## 4. LLM の呼び出し

- 方式：eigo dojo（`/home/tomo/project/003_eigo/eigo_dojo/backend/app/llm.py`）と同じく、OpenAI 互換の chat/completions を httpx で呼ぶ。キーは環境変数から読む（現在のシェルに Gemini・Groq・Cerebras・Mistral・DeepSeek・OpenRouter のキー名が設定済み [データ]。値は確認していない）。
- **自動フォールバック**：既定は Gemini 2.5 Flash → Groq → Cerebras → Mistral → DeepSeek（有料、最後の手段）の順。トークン上限・レート制限・エラーで次へ進む。プロバイダの順番・モデル・タイムアウト・1 分あたりの呼び出し上限は `config.yaml` の `llm:` に置く。
- リポジトリをまたいだ import はしない。必要最小限のクライアント（呼び出し・フォールバック・レート制限）をこのリポジトリに書く [推論：依存関係を単純に保つため]。
- Web 検索（Gemini のグラウンディング）：OpenAI 互換のエンドポイントでは使えないとする二次情報がある [報道]。ネイティブのエンドポイントと `google_search` ツールなら使える可能性がある（公式未確認）。**フェーズ 1 では使わず**、取得した一次情報だけで調査する。

## 5. 記録

`docs/record_design.md` で設計済みの `reviews` テーブルに保存する（1 行 = 実行 × 銘柄）。

| 列 | 内容 |
|---|---|
| run_id, ticker | どの実行のどの銘柄か |
| suggestion, reason_forgotten, source_type, chokepoint, exposure_pct, closing_paths | T1〜T5 の結論 |
| one_off_items, capital_actions | T2・T3 |
| evidence | 照合できた引用（JSON） |
| verified_ratio | 引用の照合率 |
| llm_model, prompt_version, llm_prompt, llm_answer | 再現と比較のため |
| human_decision, decided_at | 人の最終判断（あとで記入） |

答え合わせ（`docs/record_design.md` Q7）：人が採用した銘柄・LLM が採用を提案した銘柄・落選させた銘柄の、6 か月後・1 年後の超過騰落率を比べ、二次の価値を測る。

## 6. 規模と費用 [推論]

- 二次候補 50 銘柄 × タスク 5 本 ≒ 250 回/実行（四半期に 1 回）。無料枠の範囲に収まる見込み。収まらなければフォールバックで有料の DeepSeek が使われるので、1 回あたりの上限（呼び出し回数）を config に置く。
- 取得した文書は書類 ID ごとに保存し、同じ文書を二度取りにいかない。
